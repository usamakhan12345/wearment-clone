# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

Next.js 16 (App Router, Turbopack) + React 19 + strict TypeScript, styled with **SCSS (not Tailwind)**, with **Payload CMS 3 embedded in the same Next.js app** and **MongoDB** as the database. Package manager is **npm**. All `payload` / `@payloadcms/*` packages are pinned to the exact same version and must be upgraded together.

## Commands

```bash
npm run db:up            # local MongoDB via docker compose (localhost:27017)
npm run dev              # http://localhost:3000, admin at /admin
npm run build && npm start
npm run lint             # ESLint
npm run lint:styles      # Stylelint (SCSS)
npm run typecheck        # tsc --noEmit
npm test                 # Vitest; single file: npx vitest run src/lib/slugify.test.ts
npm run generate:types   # regenerate src/payload-types.ts after changing collection fields
npm run generate:importmap  # after adding custom admin components
```

`.env` (copy from `.env.example`) must define `MONGODB_URI` and `PAYLOAD_SECRET`; `src/config/env.ts` throws at startup if either is missing, which also applies to `next build`.

## Architecture

- **Two route groups, two root layouts.** `src/app/(frontend)` is the public site; `src/app/(payload)` is Payload's admin UI and REST/GraphQL API. Files under `(payload)` are generated by Payload (headers say DO NOT MODIFY); customise via `payload.config.ts` or `(payload)/custom.scss`, not by editing them. Static `/admin` and `/api` win over the frontend's dynamic `[slug]` route.
- **Frontend never talks to Payload directly from routes.** Route files call functions in `src/services/` (data-access layer), which use `getPayloadClient()` from `src/lib/payload.ts`. These queries pass `overrideAccess: false` on purpose: the Payload Local API bypasses access control by default, which would leak drafts. Keep that when adding queries.
- **Access rules are reusable functions** in `src/access/`; collections in `src/collections/` compose them. Collections with `versions.drafts` use `isAuthenticatedOrPublished`.
- **Types flow from the CMS schema.** `src/payload-types.ts` is generated; never edit it. Run `generate:types` after changing fields, then use the generated types (e.g. `Page`) in services and components.
- **Frontend pages are `force-dynamic`** (set in `(frontend)/layout.tsx`) because they query MongoDB per request and the build must not need a live database. Moving to ISR means adding Payload `afterChange` hooks that revalidate Next.js paths.
- **SCSS layering.** Design tokens are CSS custom properties in `src/styles/base/_root.scss` (light/dark via `prefers-color-scheme`); components consume `var(--token)` and never hard-code colours or spacing. Sass-only helpers (breakpoint `up()` mixin, `focus-ring`, `visually-hidden`) live in `src/styles/abstracts` and are consumed with `@use 'abstracts' as *;`, which resolves from any depth because `next.config.ts` sets `sassOptions.loadPaths` to `src/styles`. Component styles are co-located CSS Modules (`Foo.module.scss`); `global.scss` is imported once from the frontend layout.
- **Env access is centralised** in `src/config/env.ts` (`parseEnv`, a pure function taking a source object). Don't read `process.env` elsewhere.

## Environment note

Payload 3.94 declares `engines.node` as `^22.23.5 || ^24.22.3 || >=26.13.1`. The dev machine was on Node 24.21.0 when this was set up, so `npm install` prints an `EBADENGINE` warning until Node is upgraded.
