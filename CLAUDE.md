# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Payload-driven rebuild of the Shopify storefront wearments.com (the owner authorised the copy), now branded **AMORA** (see "Brand"). Every piece of storefront content (products, collections, pages, homepage sections, header/footer, images) lives in Payload/MongoDB and was imported from the live site by `scripts/import-wearments`.

Stack: Next.js 16 (App Router, Turbopack) + React 19 + strict TypeScript, styled with **SCSS (not Tailwind)**, **Payload CMS 3 embedded in the same Next.js app**, **MongoDB**. Package manager is **npm**. All `payload` / `@payloadcms/*` packages are pinned to the exact same version and must be upgraded together.

## Commands

```bash
npm run dev              # http://localhost:3000, admin at /admin
npm run build && npm start
npm run lint             # ESLint
npm run lint:styles      # Stylelint (SCSS)
npm run typecheck        # tsc --noEmit
npm test                 # Vitest; single file: npx vitest run src/lib/slugify.test.ts
npm run generate:types   # regenerate src/payload-types.ts after changing collections/globals/blocks
npm run generate:importmap  # after adding custom admin components
npm run import:wearments    # (re)import the storefront; see "Importer" below
npm run media:migrate       # move image files from local disk into MongoDB GridFS; see "Media storage"
```

`.env` must define `MONGODB_URI` and `PAYLOAD_SECRET`; optional `SITE_URL` (public origin, used for `metadataBase`). `src/config/env.ts` validates them and throws at startup, which also applies to `next build`. **The current `.env` points at the hosted Atlas database (`shemi_product`), so anything that writes (importer, admin, newsletter signups) writes there.** Docker Desktop would not start on the original dev machine, so `npm run db:up` (docker compose) is untested.

## Architecture

- **Two route groups, two root layouts.** `src/app/(frontend)` is the public site; `src/app/(payload)` is Payload's admin UI and REST/GraphQL API. Files under `(payload)` are generated by Payload (headers say DO NOT MODIFY); customise via `payload.config.ts` or `(payload)/custom.scss`.
- **URLs mirror Shopify** so old links keep working: `/` (the `pages` doc with slug `home`, `HOME_PAGE_SLUG`), `/collections/[handle]` (`all` is a virtual collection), `/products/[handle]`, `/pages/[slug]`, `/search`. `/collections/x/products/y` redirects to `/products/y`.
- **Content model.** Collections: `products` (variants/options, ordered `images`; `price`/`compareAtPrice`/`available` are derived from `variants` by a `beforeChange` hook, never edit by hand), `categories` (labelled "Collections"), `pages` (a `layout` block builder for the homepage plus a rich-text `content` for text pages), `media`, `subscribers`, `users`. Globals: `site-settings`, `header`, `footer`, `product-page-settings` (shared product-page notices, coupons, info panels, trust badges, testimonials). Handles are generated by `src/fields/handle.ts`, which strips non-ASCII (a few Shopify handles contained emoji, so always key products by the stored handle, `slugify(shopifyHandle)`).
- **Homepage blocks have a strict pairing.** Schema in `src/blocks/*` (registered in `src/blocks/index.ts`) and renderer in `src/components/blocks/*`; `RenderBlocks.tsx` is an exhaustive `switch` on `blockType`, so adding a block means touching both and regenerating types. Don't name a field `collection`: Mongoose reserves it (the product showcase block uses `category`).
- **Routes never query Payload directly.** They call `src/services/*` (products, categories, pages, globals, product-page), which use `getPayloadClient()`. All queries pass `overrideAccess: false` on purpose: the Local API bypasses access control by default and would leak drafts. Keep that.
- **Catalog query logic is pure and tested** in `src/lib/catalog/` (URL params -> validated query -> Payload `where`/sort). Never pass raw search params to Payload.
- **Media storage: MongoDB GridFS, never disk.** The `media` collection has no local folder (Vercel has no writable/persistent disk). `cloudStoragePlugin` in `payload.config.ts` plugs in `src/storage/gridfs.ts`, which stores each file in the `media_files` GridFS bucket of the same database and serves it at `/api/media/file/<filename>` (ETag/304, immutable cache headers, CSP sandbox for SVG). Uploads are converted to WebP, the original is capped at 2000px wide and one `card` (640px) rendition is generated; that is ~290 KB per image, ~250 MB for the whole catalog, which matters because a free Atlas cluster holds 512 MB. There is deliberately no `large` rendition: `toImageData(media, 'original')` is the full-size image and `'card'` the small one. `npm run media:migrate` (`MIGRATE_LIMIT`, `MIGRATE_FORCE=1`) moves files from `./media` / `.import-cache/images` into GridFS; it keeps document ids, so nothing referencing media needs re-linking.
- **Types flow from the schema.** `src/payload-types.ts` is generated; never edit it.
- **Frontend pages are `force-dynamic`** (`(frontend)/layout.tsx`): they query MongoDB per request and the build must not need a live database. Moving to ISR means Payload `afterChange` hooks that revalidate paths.
- **SCSS layering.** Design tokens are CSS custom properties in `src/styles/base/_root.scss` (light only, mirrors the original); components use `var(--token)` and never hard-code colours/spacing. Sass helpers (`up()` breakpoint mixin, `focus-ring`, `button-solid`, `section-heading`, ...) live in `src/styles/abstracts` and are consumed with `@use 'abstracts' as *;` from any depth (`next.config.ts` sets `sassOptions.loadPaths`). Component styles are co-located CSS Modules. Fonts (Poppins body, Jost headings) come from `src/styles/fonts.ts` via next/font and need network at build/dev time.
- **Env access is centralised** in `src/config/env.ts` (`parseEnv`, pure). Don't read `process.env` elsewhere (the Payload CLI scripts pass it in).

## Importer (`scripts/import-wearments`)

Pulls the live store's public JSON (`/products.json`, `/collections.json`, collection membership), page HTML and homepage content, downloads images, and writes everything to Payload. Idempotent: records match by handle/slug, images by `media.sourceUrl`; downloaded files are cached in `.import-cache/` (gitignored), so re-runs are fast.

- Options are env vars, not CLI args (`payload run` strips arguments): `IMPORT_ONLY=catalog,pages,site`, `IMPORT_LIMIT=5`.
- `payload run` exits when the script module finishes evaluating, so the entry point must use top-level `await`.
- Homepage/footer/product-page content that is not in the public JSON is embedded in `scripts/import-wearments/site.ts` and `data/*.ts` (Instagram image URLs are signed and expire; only the cached files matter after the first run).
- The importer creates media documents through Payload, so images go straight into GridFS (see "Media storage"); the download cache in `.import-cache/images` is also the source for `npm run media:migrate`.

## Brand (AMORA)

The store was renamed from Wearments to **AMORA**. The brand name is content, not code: nothing under `src/` hard-codes it; the site name comes from the `site-settings` global.

- `scripts/rebrand/` holds the rename tooling: `scan.ts` (read-only: lists every remaining old-name hit in the DB and GridFS; `npm run rebrand:scan`), `backup.ts` (JSON export to the gitignored `.rebrand-backup/`), `apply.ts` (`npm run rebrand` is a dry run, `npm run rebrand:apply` writes; phases `text,globals,media`) and `render-assets.ts` (draws the AMORA logo and banners into `brand-assets/amora/` with sharp and Jost, `brand-assets/fonts`, SIL OFL).
- **The importer still produces the old brand** (it faithfully clones wearments.com, whose origin URLs must keep that name). After any re-import run `npm run rebrand:apply`. It is idempotent, finds the imported logo/banners by their `wearments-*` filenames, and swaps them in place (same document ids, new `amora-*` filenames) so references need no re-linking.
- `apply.ts` replaces only the capitalised name (`Wearments`, `WEARMENTS150` -> `AMORA150`). Lower-case occurrences are real email addresses, the `wearments.com` domain and social handles; they are left until the owner supplies the new ones. The Instagram/Facebook links were cleared for the same reason.
- The product photos and the Instagram grid images still show the old name printed on garment hang tags, neck labels and shopping bags. They cannot be text-replaced; they need new photos.

## Not implemented (out of scope so far)

Cart, checkout, orders, payments and customer accounts. The header account/cart icons and the product page's BUY NOW / Add To Cart buttons are intentionally disabled (`aria-disabled`, "Coming soon"); don't replace them with dead links. The Judge.me reviews widget, AI chat widget and "recently purchased" toast of the original are third-party apps and were not cloned. The live blog has no posts, and the footer's "Blog" / "Reviews" links had no real targets, so they were omitted.

## Environment note

Payload 3.94 declares `engines.node` as `^22.23.5 || ^24.22.3 || >=26.13.1`. The dev machine was on Node 24.21.0, so `npm install` prints an `EBADENGINE` warning until Node is upgraded (everything ran fine on 24.21.0).
